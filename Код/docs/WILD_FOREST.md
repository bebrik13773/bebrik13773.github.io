## 2. Форматы данных

### Координаты и мир
- Единицы — метры; `x` вправо, `z` вперёд, `y` вверх (как в Three.js). Город в (0, 0). Край мира ±100 км.
- **Чанк** 32×32 м: `cx = floor(x/32)` (именно `floor`, не отбрасывание дроби: иначе ломаются отрицательные координаты).
- **Клетка** 4×4 м, 64 на чанк, максимум одно дерево. Индекс в чанке `ci = lz*8 + lx`.
- **id дерева** = `"cx:cz:ci"`, например `3:-2:17`. Тот же id — ключ записи в `forest_chunk_changes`.
- **Плитка дороги** 4×4 м: `tx = floor(x/4)`, `tz = floor(z/4)`.
- Для генерации координаты переводятся в целые дециметры (`X = floor(x*10)`), без `float`. Хеш/шум — беззнаковые 32 бита, шум в Q16 (см. раздел 6.2 плана).
- `tier = min(10, floor(r/500))`, где `r` — расстояние до города. Зоны: опушка < 600 м, чаща 600–1500 м, глушь > 1500 м.

### Типы действий в `sync` (поле `type`)
`move` (опорные точки), `chop_done`, `pickup`, `drop`, `eat`, `build_tap`, `plant`, `water`, `cast`, `hook`, `scare`, `emote`, `chat`. Новые типы добавляются в своих пунктах; неизвестный тип получает `bad_state`.

Пакет: `{seq, client_ts, pos{x,z,ry}, anim, view{cx,cz,r}, cursor, actions[{a,type,...}]}`.
Ответ: `{ok, server_ts, ack, results[{a,ok,error?,reward?}], state, near, changes{cursor,items}, messages, events, next_sync_ms}`.
- `a` — номер действия, растёт; сервер помнит последний обработанный, повтор игнорируется (идемпотентность).
- Ошибка одного действия не роняет пакет: у каждого свой `ok` и код.
- При ошибке позиции сервер возвращает `correct_pos`, клиент плавно возвращает бобра.
- `next_sync_ms` задаёт сервер (простой — реже, торг — чаще, перегрузка — реже).

### Единый формат ответов API
Успех: `{"ok": true, "data": {...}}`. Ошибка: `{"ok": false, "error": "<код>", "message": "<текст для игрока>"}` + подходящий HTTP-статус. Тексты для игрока — только по-русски и без жаргона.

### Коды ошибок
| Код | Когда |
|-----|-------|
| `too_fast` | больше ударов/тапов, чем разрешает бюджет, или скорость выше допустимой |
| `too_far` | дальше допустимого радиуса от дерева, предмета, постройки |
| `no_energy` | не хватает энергии на действие |
| `sleeping` | бобёр спит (энергия кончилась): рубить и ходить нельзя, пока не отдохнёт или не поест (ДЛ-12) |
| `no_tree` | дерева нет по генерации мира |
| `tree_gone` | дерево уже срублено (в т. ч. другим игроком), энергия возвращается на 50% |
| `bad_state` | действие недопустимо в текущем состоянии |
| `no_items` | предмета или ресурса нет |
| `no_space` | не хватает места (рюкзак, склад, станок) |
| `rate_limited` | слишком частые запросы |
| `forbidden` | нет прав (в т. ч. админка) |
| `outdated` | клиент устарел, нужна перезагрузка |
| `unauthorized` | нет сессии кликера |

Файл `Код/api/forest/config.php` возвращает массив. Группы:

|--------|-----------|

| `buildings` | стоимость и тапы построек, правила места, отмена и снос |
| `upgrades` | рюкзак, выносливость, фонарь, снаряжение |
| `dam` | износ, запас офлайна, прорыв, ремонт, улучшения |
| `weather` | таблица шансов по сезонам, множители, ночная видимость |
| `trade` | покупатели, терпение, фразы торга |
| `helpers` | скорость, зарплата, найм, просрочка, храбрость |
| `beasts` | шансы встреч, лиса, волк, медведь |

Правила: в коде нет «магических чисел»; клиент получает часть конфига через `forest/config` (с версией; при несовпадении версии клиент перезапрашивает).

## 4. Лимиты бесплатного хостинга

Дата проверки: **2026-10-05**. Хостинг `bober-api.gt.tc` — InfinityFree (FTP-хост `ftpupload.net`, аккаунт `if0_*`).

| Параметр | Значение | Источник |
|----------|----------|----------|
| **Хиты в сутки** | **50 000** на аккаунт. Хит — любое обращение к серверу, **включая статические файлы** (js, css, картинки). При превышении аккаунт отключается на 24 часа | документация и форум InfinityFree |
| CPU | суточный лимит «CPU-секунд»; превышение = отключение на 24 часа; повысить нельзя | форум InfinityFree |
| Лимиты MySQL | суточный лимит нагрузки на MySQL; превышение отключает аккаунт на сутки (точное число не публикуется) | форум InfinityFree |
| Прочее | суточные лимиты RAM, I/O, entry processes (одновременных PHP-процессов) | страница поддержки InfinityFree |
| Диск / трафик | 5 ГБ, трафик без лимита (в пределах fair use) | сайт InfinityFree |
| Cron, WebSocket, фоновые процессы | нет — расчёты только лениво при запросах | решение плана |
| PHP / MySQL | PHP 8.4.25, MariaDB 11.4.13 — см. результат запуска ниже | `forest-env.php` |

| Изоляция транзакций | REPEATABLE-READ |
| `GET_LOCK` | работает |

| Диск | свободно около 5 ГБ |

**Выводы для плана**
1. **Все таблицы `forest_*` создаём с явным `ENGINE=InnoDB`.** Движок по умолчанию MyISAM не поддерживает транзакции и блокировки строк, а на них держатся рубка без гонок, обмен между игроками, найм и склад. InnoDB на хостинге доступен (3 таблицы уже на нём). Миграции в ДЛ-03 проверяют движок и при необходимости делают `ALTER TABLE ... ENGINE=InnoDB`.
2. `player_id` — `INT` (как `users.id`), чтобы совпадали типы и индексы.
3. **`max_user_connections` = 16:** одновременно открыто не больше 16 соединений к базе. Один запрос — одно соединение, закрывать сразу; тяжёлые операции (пересчёты помощников, A*) держать короткими, иначе под нагрузкой будет «Too many connections».
4. 64-битный PHP: арифметика генерации мира совпадёт с планом (`mul32` через 16-битное разбиение, приведение к беззнаковым 32 битам).
5. `apcu` доступен: им можно кешировать конфиг и мелкие горячие данные между запросами (с запасным путём без него, на хостинге его могут отключить).
6. База уже 218 МБ: проверить лимит размера БД в панели хостинга (ДЛ-38); для `forest_chunk_changes` заложить чистку старых записей (открытый вопрос про пни).
7. Часовой пояс сервера +06 (Омск), как и `Asia/Omsk` в конфиге.

## 5. Бюджет запросов

Главное ограничение игры: **50 000 хитов в сутки на весь аккаунт** — вместе со старым кликером, админкой, ботами и всей статикой.

| Состояние игрока | Интервал `sync` | Хитов в час |
|------------------|-----------------|-------------|
| Активная игра | 8 с | 450 |
| Простой (30 с без действий) | 15 с | 240 |
| Вкладка в фоне | 60 с | 60 |
| Торг/диалог | по ходу | единицы |

Расчёт ёмкости (оценка, уточняется в ДЛ-38):
- Старт одной сессии без оптимизаций: ~30–60 хитов на загрузку модулей и ресурсов, поэтому статику нужно кешировать (service worker, версия по SHA) и держать число файлов малым.
- Резервируем 30% суточных хитов старому кликеру и служебным вещам → на лес остаётся ~35 000 хитов.
- При активной игре (450 хитов/час) это ≈ **78 игрочасов в сутки**; при смеси активных и простаивающих (в среднем ~300 хитов/час) ≈ **115 игрочасов в сутки**.
- В вечерний пик это порядка **5–10 одновременных игроков** (закрытая бета этого достаточно, открытый запуск — нет).

Меры при приближении к лимиту (включаются в ДЛ-38):
1. Счётчик хитов в `forest_meta`; при 70% суточного лимита сервер увеличивает `next_sync_ms` до 12–15 с, при 90% — до 30 с и ставит очередь на новые входы.
2. Сокращение радиуса присутствия игроков и объединение ответов в один.
3. Минимум файлов: объединение модулей при деплое (или сжатие в один бандл), `Cache-Control` на статику, service worker.
4. Если не хватает — обсудить платный хостинг или вынос API (открытый вопрос 7 в разделе 6).

## 7. Как это связано с кодом кликера

- Авторизация: PHP-сессия `BOBERSESSID`, `bober_get_logged_in_user_id()` из `api/bootstrap/db.php`; игрок леса = `users.id` (`INT`).
- Подключение к БД: `bober_db_connect()` (mysqli, `utf8mb4`, часовой пояс `+06:00`). Новые таблицы с префиксом `forest_`, схема с версией в `forest_meta` и автомиграцией (ДЛ-03).
- Ответы: единый JSON-формат раздела 2 (в отличие от `bober_json_response`, где используются `success`/`message`; адаптер появится в ДЛ-03).
- Деплой: GitHub Actions заливает `Код/` по FTP при каждом пуше в `main`; новая папка `Код/games/wild-forest/` и `Код/api/forest/` едут как есть.
- PHP в контейнере разработки не запускается: серверная логика пишется чистыми функциями и проверяется страницей `tools/forest-selftest.php` на хостинге (ДЛ-03).

## 9. Серверный каркас (ДЛ-03)

| Файл | Назначение |
|------|-----------|
| `Код/api/bootstrap/forest_db.php` | `forest_config('a.b')`, `forest_db()` (одно соединение на запрос), схема с версией и автомиграцией |
| `Код/api/forest/lib/common.php` | единый формат ответов, `forest_json_in()`, `forest_require_player()`, `forest_rate_limit()`, `forest_tx()`, `forest_log()`, каталог ошибок |
| `Код/api/forest/health.php` | `GET /api/forest/health.php`: версия схемы, время сервера, режим беты (сам создаёт схему) |
| `Код/tools/forest-selftest.php` | страница самопроверки (пароль администратора): конфиг, схема, InnoDB, транзакции, лимиты |

**Схема** (версия 4, 19 таблиц `forest_*`, все `ENGINE=InnoDB`): миграция 1 — ядро (`meta`, `players`, `inventory`, `drops`, `chunk_changes`, `log`); 2 — деревня (`buildings`, `saplings`, `road_tiles`, `routes`, `dams`); 3 — люди и мета (`helpers`, `trades`, `presence`, `chat`, `ratings`, `seasons`, `event_log`); 4 — права администраторов (`admins`). Новая миграция = новая функция `forest_migration_N` и `FOREST_SCHEMA_VERSION`.
- В `forest_chunk_changes` поле называется `ckey` (в плане `key`, но это зарезервированное слово SQL); уникальный ключ `(kind, ckey)` защищает от гонок.
- Миграции идемпотентны (`CREATE TABLE IF NOT EXISTS`), идут под `GET_LOCK('forest_schema')`, повторная проверка кешируется файлом-замком на 10 минут (экономит лимит запросов). Таблицы леса не на InnoDB автоматически переводятся в InnoDB.
- Лимит частоты `forest_rate_limit(ключ, мс)` и IP-защита хранятся в APCu (запасной вариант — файл в каталоге кеша), без запросов к БД.
- `forest_require_player($conn, $withAccessRules)`: игрок берётся из сессии кликера; полная проверка банов и сессий включается флагом и отключается для «горячих» эндпоинтов (ДЛ-38).
- **Права администраторов** (решение владельца): таблица `forest_admins` (миграция 4, схема v4, 19 таблиц), роли `creative` и `moderator` (`config.php`, группа `admin`). Выдаются любому игроку из админ-панели кликера: раздел «Дикий Лес» (`Код/admin/index.php`: выдача по логину, отзыв, запись в аудит админки, кнопка «Открыть Креатив»). Функции `forest_is_admin()`, `forest_require_admin()`; `GET /api/forest/admin-access.php` сообщает клиенту роль игрока. Жёсткого id владельца нет.

## 10. Генерация мира (ДЛ-05)

Один и тот же мир строят клиент (JS) и сервер (PHP) по одному алгоритму и из одних и тех же данных.

| Файл | Что внутри |
|------|------------|
| `Код/games/wild-forest/src/shared/rng.js` | `mul32`, `mix` (murmur3 fmix32), `hash(seed,x,z,salt)`, шум значений в Q16 (`noise2`), `fbm` (4 октавы, веса 8/4/2/1), `floorDiv`, `isqrt` |
| `Код/games/wild-forest/src/shared/worldgen.js` | `createWorldGen({seed, species, biomes})`: `heightAtDm`, `biomeAtDm`, `cellAt(cx,cz,ci)`, `chunkCells`, `tierAtDm`, `zoneAtDm`, `isCityZone`, `boulderAt`, `oreAt`, `treeId`/`parseTreeId` |
| `Код/games/wild-forest/src/shared/species.json`, `biomes.json` | порядок пород и **все константы генерации** (периоды, соли, пороги биомов, плотности, шансы). Читают и JS, и PHP, поэтому числа не дублируются |
| `Код/games/wild-forest/src/world/gen.js` | клиентский загрузчик `loadWorldGen()` (fetch JSON + сид из `config.js`) |
| `Код/api/forest/lib/worldgen.php` | зеркало на PHP (`wf_wg_*`), точечная проверка клетки по id дерева: `wf_wg_cell_by_id()` |
| `Код/games/wild-forest/tests/vectors/worldgen.json` | золотые тест-векторы: 10 000 точек и 10 480 клеток основного мира, 1 500 + 1 500 для второго сида (больше 2^31), 1 500 хешей и 1 000 записей шума |

**Правила совпадения JS и PHP.** Только целые числа; хеш и шум в беззнаковых 32 битах (`mul32` в PHP разбит на 16 бит, чтобы не выйти за 64 бита); отрицательные координаты приводятся к беззнаковым маской; деление только целочисленное, для знаковых значений через `floorDiv`/`wf_wg_fdiv`; интерполяция в фиксированной точке Q16 без `float`; все смеси считаются на неотрицательных числах (поэтому `intdiv` в PHP равен `Math.floor` в JS).

**Единицы.** Ядро работает в целых дециметрах (`X = floor(x * 10)`), метровые обёртки (`heightAt`, `biomeAt`) только для удобства клиента. Клетка 4x4 м = 40x40 дм, чанк = 8x8 клеток, id дерева `cx:cz:ci`.

**Что получилось (отличия от чернового текста плана 6.3, подобрано замерами на 20-40 тысячах точек).**
- Вода: озеро при `E < 6500`; река там, где эффективное расстояние до русла `R + max(0, E - 24000) < 1800` (на высоких местах река сходит на нет, поэтому нет обрывов). Берега плавно сводятся к уровню воды (-3 м). Вода это около 3% карты.
- Болото: `M > 40000` и `E < 26000` (по черновику 45000/22000 болот было меньше 1%, около 4.5% после подбора).
- Одна клетка = один объект: приоритет руда, затем дерево, затем булыжник.
- Реки и озёра «вырезают» рельеф ниже уровня воды (-3 м), поэтому по высоте всегда можно отличить воду от суши.
- Край мира 100 км: за ним клетки пустые.
- Скорость: около 0.15 мс на чанк в контейнере без GPU (цель плана: меньше 2 мс на обычном ПК).

**Проверки.** Node: `node --test Код/games/wild-forest/tests/*.test.mjs` (хеш против эталона на BigInt, формула `mul32` для PHP, сид и плотности сверяются с `config.php`, векторы воспроизводятся текущим кодом, плотности и размеры деревьев, город без деревьев, плавность рельефа). Браузер: `python3 Код/games/wild-forest/tests/e2e_worldgen.py`. PHP: страница `tools/forest-selftest.php` (раздел «Мир»), полный прогон занимает несколько секунд, при нехватке времени на хостинге открывать с `?quick=1`. Векторы пересоздаются командой `node Код/games/wild-forest/tests/gen-vectors.mjs` (только вместе с проверкой PHP).

## 11. Управление и камера (ДЛ-08)

Клиент: `src/core/` (`gestures.js` жесты, `input.js` Pointer Events и клавиши, `camera-rig.js` камера, `track.js` журнал позиций), `src/world/` (`terrain-nav.js` проходимость воды и склонов, `nav.js` поиск пути A*, `picking.js` выбор объекта пальцем), `src/entities/hero.js` (контроллер героя), `src/shared/formulas.js` (скорость и допуск сервера). Все пороги в `config.js` (`INPUT`, `CAMERA`, `MOVE`).

- **Жесты.** Тап (быстрее 200 мс и сдвиг меньше 10 px) это действие. Один палец камеру не крутит. Два пальца: щипок = зум, поворот пальцев = вращение, сдвиг центра = вращение и наклон; жесты «залипают» после порога, дрожание игнорируется. ПК: правая кнопка вращает, колесо зумит, WASD и стрелки ходят, Q/E вращают, +/- зумят. Касания у левого и правого края экрана (14 px) игнорируются, холст с `touch-action: none`, интерфейс вне сцены тапы в мир не пропускает.
- **Камера.** Орбита вокруг бобра, дальность 6–18 м (по умолчанию 9, в портрете чуть дальше), наклон 20–70°, плавная «пружина». Не уходит под землю и за холм (приближается сразу, отъезжает плавно).
- **Тап.** Сначала объекты (деревья, позже NPC, предметы, постройки, помощники через `addTarget`), затем земля (трассировка луча по функции высоты). Дерево: подойти на ~1.8 м, встать лицом, режим «работа» (тап по тому же дереву = взмах; тап по земле выходит). Настоящая рубка приходит в ДЛ-11 (событие `workTap`).
- **Путь.** A* по сетке 1 м (до 9000 клеток, радиус 90 м), сглаживание, препятствия круглые (стволы, камни, руда из чанков), вода и склоны круче 40° непроходимы, проходимость кэшируется по чанкам. Нет пути: идём к ближайшей достижимой точке (оранжевая метка). Застревание: перестройка, потом остановка и событие `blocked`.
- **Скорость.** `v = 3.2 × (1 − 0.55 × min(1, груз/вместимость)^1.2) × (1 + дорога) × (1 + сапоги) × погода`; дорога +10/25/45%, сапоги +10%. Журнал позиций раз в секунду (`track.js`), сервер при `sync` проверяет шаг по правилу `vMax × dt × 1.35 + 3 м` (`wf_check_track`, `checkTrack`).
- **Проверки.** Node: `tests/controls.test.mjs` (формулы, жесты, камера, журнал), `tests/nav.test.mjs` (путь, герой, выбор объекта, реальный лес). Браузер: `python3 Код/games/wild-forest/tests/e2e_controls.py` (касания через CDP). PHP: selftest, раздел 4а.

## 13. Профиль игрока и появление (ДЛ-10)

- **Эндпоинты.** `GET forest/state` (полное состояние при входе; нет профиля → `bad_state` с `extra.need_join`), `POST forest/join` (создаёт игрока и ставит на поляну, повторный вызов возвращает уже созданного), `POST forest/sync` (пакет версии 1). Все ответы в формате `{ok, data}` / `{ok:false, error, message}`.
- **Где появляется.** Кандидат номер k детерминирован по `hash(id игрока, k, фаза)`: 70% попыток в кольце 800..2500 м от города, остальные 600..4000 м. Подходит точка, если вокруг (центр и 8 точек на 24 м) только лес (хвойный, лиственный, берёза) и перепад высот не больше 5 м. Не нашли за 30 попыток, берём 30 попыток в 600..6000 м с перепадом 8 м, затем до 200 запасных (16 м). Не ближе 150 м к чужому спавну (рамка по `forest_players.spawn_x/z`); гонка двух игроков закрыта уникальной записью `spawn_cell` (клетка 150×150 м) в `forest_chunk_changes`.
- **Что создаётся.** Строка `forest_players` (энергия 100, 50 монет, топор ур.1, хотбар `['axe']`), запись `clearing` (круг 12 м), пруд в 20 м от центра под детерминированным углом (запись `pond` с точкой плотины и ещё один `clearing` радиусом 8 м, чтобы на пруду не росли деревья), строка `forest_dams` (ур.1, прочность 100). Имя деревни пока заглушка «Поляна <id>», настоящие имена придут в ДЛ-15.
- **Уровень.** С уровня l на l+1 нужно `round(100 × l^1.6)` опыта, максимум 50 (`shared/formulas.js`: `xpToNext`, `levelFromXp`, зеркало `lib/formulas.php`). Опыт начисляется с ДЛ-11.
- **sync v1.** Клиент шлёт `{seq, client_ts, pos:{x,z,ry}, actions:[{a, type}], background}`. Сервер: лимит 1 запрос в 3 с, номера действий `a` идемпотентны (последний обработанный в `stats_json.last_a`, повтор получает `dup:true`), позиция проверяется по `vMax × dt × 1.35 + 3 м` (dt не больше 120 с, vMax пока самый щедрый: асфальт и сапоги), при превышении возвращается `correct_pos` и запись `move_far` в `forest_log`. «Запас офлайна» плотины (`grace_until`) продлевается только настоящими действиями или движением. Ответ: `ack`, `server_ts`, `server_ms`, `results`, `state` (энергия, монеты, вес, рюкзак, уровень), `next_sync_ms` (8 с в игре, 15 с после 30 с простоя, 60 с в фоне). Все типы действий пока отклоняются кодом `bad_state`, настоящие приходят с рубкой (ДЛ-11) и подбором (ДЛ-13).
- **Клиент.** `net/session.js` (health → state → join), `net/queue.js` (очередь действий с номерами и повтором), `net/sync.js` (цикл, пауза при ошибках 8 → 16 → 30 с, учёт `rate_limited`, часы по `server_ms`), `net/apply-state.js` (HUD и рюкзак из состояния), `world/village-props.js` (пруд и плотина из брёвен). Без входа в аккаунт или без сервера игра работает как раньше (временная поляна), прогресс не сохраняется, показывается сообщение.
- **Проверки.** Node: `tests/spawn.test.mjs` (мир, цепочка из 300 игроков, пруд, уровни, совпадение констант с `config.php`), `tests/net.test.mjs` (очередь, sync, сессия). Золотые векторы `tests/vectors/spawn.json` (`node tests/gen-spawn-vectors.mjs`), их сверяет `tools/forest-selftest.php` (раздел «Появление», плюс запись и уборка тестового игрока в БД). Браузер: `python3 tests/e2e_session.py` (сервер подменяется через route).

## 14. Рубка деревьев (ДЛ-11)

- **Клиент.** Тап по дереву: бобёр подходит и начинает работу (`world/chop.js`, `world/chop-flow.js`). Каждый тап по тому же дереву это удар, не чаще 6 в секунду. Число ударов `ceil(HP / сила топора)`, `HP = 8 × H × k_размер × (1 + 0.30 × tier)` (`shared/formulas.js`, зеркало `api/forest/lib/chop.php`). Над деревом шкала прочности (`ui/chop-bar.js`). Прогресс по дереву только локальный и сбрасывается, если уйти от дерева. После последнего удара дерево сразу заменяется пнём (оптимистично) и в очередь уходит действие `chop_done`: `{tree, hits, t0, t1, px, pz}` (позиция бобра в момент рубки). Отправка сразу после падения, но не чаще, чем раз в 3.2 с.
- **Сервер** (`api/forest/lib/actions.php`, `chop.php`, `sync.php`). Весь пакет `sync` идёт в одной транзакции с блокировкой строки игрока. Проверки `wf_chop_validate` по порядку: есть ли дерево по генерации и не в `clearing` (`no_tree`), дальность до дерева 3.5 м и правдоподобность заявленной позиции относительно прошлой и новой позиции сервера (`too_far`), уже срублено (`tree_gone`, не страйк), число ударов не меньше нужного (`too_fast`), окно меток `t0..t1` не короче возможного, хватает энергии (`no_energy`), бюджет тапов: ведро 40, +6 в секунду (`too_fast`). Запись `tree_felled` создаётся `INSERT IGNORE` по уникальному ключу `(kind, ckey)`: при гонке выигрывает первый, проигравший получает `tree_gone` и теряет половину энергии рубки.
- **Награда.** Брёвна по породе и размеру (таблица 8.2), опыт по HP дерева, дерево-сокровище даёт находку по `trees.treasure_loot` (монеты 50–300, руда или семя редкой породы), всё детерминированно по id дерева. Каждое бревно отдельным предметом в `forest_drops` вокруг пня (радиус 1.0–2.2 м, 60 секунд видит только срубивший, живёт 15 минут). Подбор придёт в ДЛ-13: пока предметы только лежат на земле.
- **Страйки.** `too_far`, `too_fast`, несуществующее дерево и т.п. записываются в `forest_log` и в скользящее окно 10 минут: 1–3 мягко, 4–7 награда ×0.5, 8 блокировка на 10 минут. Автобана нет.
- **Энергия.** Рубка списывает `ударов × 0.5`. Настоящие правила энергии описаны в разделе 15 (ДЛ-12).
- **При входе** `forest/state` отдаёт срубленные деревья и выпавшие предметы в радиусе 8 чанков (до потока изменений ДЛ-21 чужие рубки вне этой зоны в течение сессии не видны). Отказ сервера на клиенте возвращает дерево (`chunks.unfell`), кроме `tree_gone` и `no_tree`.
- **Ещё не сделано** (по плану других пунктов): щепки, дрожание кроны, анимация падения и звуки (ДЛ-31), подбор брёвен (ДЛ-13), рубка чужих/общих деревьев и защита территории деревни (ДЛ-21).
- **Проверки.** Node: `tests/chop.test.mjs` (формулы, баланс совпадает с `config.php`, бюджет тапов, клиентская рубка и связка на подменённых зависимостях), векторы `tests/vectors/chop.json` (`node tests/gen-chop-vectors.mjs`), которые сверяет `tools/forest-selftest.php` (раздел «Рубка»: формулы, таблица кейсов проверки, страйки, находки, места выпадения). Браузер: `python3 tests/e2e_chop.py` (тап, подход, удары, пень, брёвна, откат при отказе).

## 15. Энергия, сон и еда (ДЛ-12)

- **Ленивый расчёт** (`api/forest/lib/energy.php`, `wf_energy_tick`). В начале каждого `sync` сервер считает энергию за время с прошлого расчёта (`energy_ts`): расход на ходьбу 0.015 за метр пути (множитель погоды придёт в ДЛ-28), затем восстановление. Фоновых процессов нет.
- **Скорость восстановления, в секунду.** Стоял на месте и ничего не делал: 0.1; рядом с готовым домом (6 м, постройка `house` в состоянии `ready`, придёт в ДЛ-17): 1.0; в движении или за работой: 0; во сне: 0.2 (дома 1.0). В расчёт идёт не больше `limits.rest_credit_cap_s` = 120 секунд между sync, поэтому закрытая вкладка энергию не копит.
- **Сон.** Энергия на нуле (после ходьбы или рубки): `stats_json.sleep = 1`, бобёр засыпает на месте. Спящий не рубит (результат действия `sleeping`, дерево возвращается), не ходит (шаг дальше метра откатывается `correct_pos` без страйка), просыпается при энергии не ниже `hero.wake_energy` = 20 (около 100 секунд). Звери (ДЛ-30) во сне нападают вдвое чаще.
- **Еда.** Действие `eat {item}` (`fish` и `fish_small` +25, `fish_big` +45): рыба списывается из рюкзака, пауза между приёмами 5 секунд (`too_fast`), нет рыбы: `no_items`, энергия почти полная: `bad_state` с `full:true`. Поевший спящий просыпается, если набралось 20. Рыба появится в ДЛ-27.
- **Состояние для клиента.** `state.sleeping` и `state.wake_energy` приходят в каждом ответе. Клиент (`world/energy-flow.js`) укладывает бобра спать (`world.setSleeping`), игнорирует тапы и клавиши, показывает 😴 в HUD и сообщает о засыпании и пробуждении; еда из панели рюкзака отправляет `eat`, бобёр жуёт 3 секунды.
- **Проверки.** Node: `tests/energy.test.mjs`, векторы `tests/vectors/energy.json` (`node tests/gen-energy-vectors.mjs`, 720 шагов); PHP: раздел «Энергия» на `tools/forest-selftest.php` по тем же векторам.
- **Ещё не сделано** (по плану других пунктов): кнопка «лечь спать» у дома (ДЛ-17), погодные множители расхода (ДЛ-28), ловля рыбы (ДЛ-27), нападения на спящего (ДЛ-30).

## 17. Рюкзак, вес ноши и подбор (ДЛ-13)

Чистые функции: `api/forest/lib/pack_weight.php` (`wf_pack_item_kg`, `wf_pack_kg`, `wf_pack_fit`, `wf_pack_move_load`) и зеркало `PACK` в `shared/formulas.js`.
- **Действие `pickup {drop, px, pz}`** (`lib/pack.php`). Сервер блокирует строку предмета, проверяет срок жизни и защиту владельца (первые 60 секунд чужой предмет «не виден»), дальность не больше 3 м от позиции бобра и допуск перемещения. Если рюкзак не вмещает всю стопку, берётся, сколько влезает, остаток лежит дальше (`left`). Ошибки: `no_items` (нет, просрочен, чужой), `too_far`, `no_space`, `sleeping`.
- **Действие `drop {item, qty}`.** Предмет списывается из рюкзака и ложится в 1.2 м от бобра (направление по номеру действия), владелец 60 секунд, живёт `trees.chop.drop_ttl_s`. Не больше 200 штук за раз и 60 живых брошенных стопок на игрока (`rate_limited`). В ответе `drop` с `id`, координатами и `ttl`.
- **Скорость и вес.** Сервер проверяет перемещение с учётом груза: `wf_sync_check_move(..., capacity, load)` берёт скорость по той же формуле, что клиент (`v = 3.2 × (1 − 0.55 × (груз/вместимость)^1.2)`, без дорог и сапог до ДЛ-24 и ДЛ-18). Груз для проверки равен весу рюкзака минус брошенное в этом же пакете, поэтому «бросил и побежал» честен, а «тяжёлый бегун» откатывается.
- **Срок жизни.** Просроченные предметы удаляются порциями (`pack.gc_limit`) при входе и при броске; клиент убирает их с экрана по `ttl`.
- **Клиент** (`world/pack-flow.js`). Тап по лежащему предмету: бобёр подходит и подбирает. Автоподбор: брёвна в радиусе 1.5 м (настройка «Автоподбор брёвен» в меню, по умолчанию включена), но не брошенные самим игроком, пока он от них не отошёл на 2.5 м. Подбор и бросок сразу меняют рюкзак на экране, точное состояние приходит в ответе sync. Вес сразу меняет скорость бобра (`world.setSpeedMods`).
- **Проверки.** Node: `tests/pack.test.mjs` (формулы, поток подбора и броска на подменённых зависимостях, баланс совпадает с `config.php`), векторы `tests/vectors/pack.json` (`node tests/gen-pack-vectors.mjs`), которые сверяет раздел «Рюкзак» на `tools/forest-selftest.php`. Браузер: `python3 tests/e2e_pack.py`.
- **Ещё не сделано** (по плану других пунктов): чужие брошенные предметы видны только при входе (поток изменений мира в ДЛ-21), точный вес бревна по размеру дерева, сдача в склад (ДЛ-14), еда из рюкзака рыбой (ДЛ-27).

## 16. Доработка бобра и рубки (#61)

- **Модель бобра** (entities/beaver-model.js): 17 костей (добавлены предплечья и стопы), руки с локтем, плечом и пальцами с коготками, стопы с пальцами, гладкий хвост-лопата с тёмной каймой и тремя желобками, маленькие круглые ушки по бокам головы, без «ирокеза». Рюкзак: мешок, клапан, передний карман; лямки идут трубками по поверхности туловища (с выносом 1.8 см), нагрудный ремень. Бюджеты треугольников подняты до 5200 (высокое) и 2300 (низкое).
- **Топор** лежит в правой кисти рукоятью вперёд, лезвием вниз; наклон рукояти равен сумме углов плеча, локтя и кисти (см. шапку beaver-anim.js).
- **Анимации** переписаны: перенос веса и взгляд в ожидании, перекат стопы, качание таза и скрутка корпуса при ходьбе, локти и хвост; рубка с замахом, выпадом, отдачей, широкой стойкой и хвостом-противовесом.
- **Рубка**: бобёр подходит на радиус ствола плюс MOVE.chopReach (головка топора достаёт до коры). Дерево на время рубки снимается с чанка и показывается отдельным мешем (world/tree-fx.js): дрожит от ударов, на стволе растёт светлая зарубка, летят щепки, срубленное падает от бобра и уходит под землю. Если бобёр ушёл, дерево возвращается без перестройки чанка.
- **Шкала рубки** стоит рядом с деревом (проекция точки у ствола), показывает неровный прогресс (каждый удар разной силы, итог ровно 1); сервер считает по-прежнему честные удары.
- **Пни** живут минуту (WORLD.stumpLifeMs) и пока есть, мешают ходить. Срубленное при входе в игру пней не даёт.
- **Проходимость**: пруд и плотина добавлены как круглые препятствия (chunks.addBlocker), вода на рельефе не проходится (waterTolerance −0.15 м).
- **Контур** бобра тоньше и растёт с отдалением камеры как корень из расстояния.
- **Уведомления** в центре исчезают через минуту, липкие предупреждения остаются.
